## Положительные находки

1. Секрет `GIGACHAT_AUTH_KEY` живёт только на сервере, клиенту уходит лишь булев `ai` из `/api/health`; в документации и `PROMPT_EXAMPLE.md` — плейсхолдеры, не реальные ключи.
2. `.gitignore` закрывает `.env`, `candidates.json`, `candidates.json.tmp`, `.temp/`, `node_modules/`, бинарные файлы.
3. Безопасный вывод: весь пользовательский текст рендерится через `textContent` / `createTextNode` / `.value`; единственный `innerHTML` — очистка списка (`script.js:593`). XSS не найден.
4. Лимиты ввода: JSON-body 600кб, текст резюме ≤60 000, поля structured ≤4000 — защита от OOM и раздувания базы.
5. Целостность базы: атомарная запись `tmp` + `rename` (`server.js:243–247`), загрузка с фильтрацией мусорных записей.
6. Надёжные исходящие вызовы: таймаут 60с, retry 401 с re-auth, обработка `finish_reason=blacklist`, явный корневой сертификат НУЦ Минцифры + `tls.rootCertificates`.
7. Статика по белому списку файлов, 404-фолбэк, корректные MIME-типы — path traversal и directory listing исключены.
8. Малая CSRF-поверхность: CORS не настроен, JSON-POST не является «simple request» — браузерные cross-site атаки на API не проходят.
9. `npm audit` — 0 уязвимостей (critical/high/moderate/low/info = 0); `package-lock.json` на месте; зависимости сведены к `express` + `dotenv` (+ `playwright-core` dev).
10. Автотесты: 75 кейсов эвристики + 14 API-кейсов; `node --check` и регресс описаны в памятке; в `КОМАНДЫ_СЕРВЕР.md` есть раздел «Безопасность».
11. Презентация `presentation.html` самодостаточна (всё inline/base64) — открывается по `file://` без сервера и внешних запросов.

## Известные ограничения

- Содержимое `.env`, `.env.example1`, `.env.example2` аудитом не проверялось (запрет доступа) — верификация только вручную владельцем.
- Не выполнялись: нагрузочный тест, пентест извне, юридическая оценка соответствия 152-ФЗ.
- Режим без TLS приемлем только на `localhost`; публичный контур требует reverse-proxy — в плане ниже, не реализовано.
- `localStorage`-режим — осознанный офлайн-фолбэк, а не отказ от серверного хранения.
- GitHub-ссылка в презентации — заглушка до публикации репозитория.
- Фактическое время ответа GigaChat и поведение при сетевых сбоях в реальной эксплуатации не измерялись.

## План устранения проблем

**Этап 0 — блокеры публикации (без этого не выкладывать):**
1. Auth Bearer на `/api/candidates*` и `/api/extract` + `crypto.timingSafeEqual`; по умолчанию слушать `127.0.0.1` (строки 1–2).
2. Rate limit на `/api/extract` — 10/мин на IP → 429 (строка 3).
3. `csvCell`: префикс `'` для ячеек `=+-@`; не сбрасывать форму при неуспешном `addCandidate` + видимое сообщение об ошибке (строки 4–5).
4. `<meta name="viewport">` + `@media (max-width:560px)` для тулбара и правки (строки 6–7).

**Этап 1 — сразу после публикации:**
5. Подключить `api-test.js` к `npm test` на изолированной базе/порту (строка 10).
6. Обобщить ответ 502, детали — в серверный лог (строка 11).
7. Исправить `serverMode` при HTTP ≠ 2xx (строка 13).
8. Скрыть экспорт и список до авторизации (строка 9).

**Этап 2 — прод-контур и гигиена:**
9. Reverse-proxy с TLS, `helmet()`, cap длины `q`, CI на PR (строка 14).
10. Кнопка очистки `localStorage` + предупреждение/TTL (строка 8).
11. Ручная верификация `.env.example*` в git-истории (строка 12).
12. Вынести эвристику в модуль вместо `eval` в тестах (строка 15).

**Критерии пересмотра решения:** статусы строк 1–10 переведены в «исправлено»; `npm test` зелёный; ручные curl-сценарии из колонки «проверка после исправления» подтверждены.

## Финальное решение о готовности релиза

**Не готов к публикации.**

Основание: критический риск утечки и порчи персональных данных (отсутствие авторизации при открытом сетевом интерфейсе), финансовый риск неограниченного расхода квоты GigaChat, инъекция формул в CSV-экспорте, потеря пользовательского ввода и неработоспособная мобильная версия. Пересмотр возможен после закрытия Этапа 0 (строки 1–7 таблицы) и подтверждения проверок из колонки «проверка после исправления».
